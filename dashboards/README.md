# Dashboards

Five dashboards, one per store Grafana can query, generated by
`mikroscope dashboards gen` in Grafana's shareable export format: the
datasource is a `${DS_MIKROSCOPE}` placeholder declared in `__inputs`, the
`uid` is fixed (`mikroscope-<store>`) so a re-import updates in place, and
there is no `id`. Beside them, three files of Grafana alert rules.

The panel counts are the panels in each file as generated on 2026-09-24
(commit af277a4, 1.2.0), rows not counted.

| File | Panels | Store |
|---|---|---|
| `mikroscope-influxdb.json` | 177 | InfluxDB 3 (SQL; every query is time-bounded, as InfluxDB 3 Core requires) |
| `mikroscope-prometheus.json` | 135 | Prometheus scraping the collector's `/metrics` (which carries everything the agent's does plus the collector's own derived and detection families) |
| `mikroscope-postgres.json` | 161 | PostgreSQL, written by `--postgres` or by applying the `--sql` script |
| `mikroscope-graphite.json` | 41 | Graphite, from `--graphite` |
| `mikroscope-elasticsearch.json` | 30 | Elasticsearch, from `--elastic` |
| `mikroscope-alerts-influxdb.yaml`, `mikroscope-alerts-postgres.yaml`, `mikroscope-alerts-prometheus.yaml` | 14 / 11 / 15 rules | Grafana unified-alerting provisioning; replace `DS_UID_PLACEHOLDER` with your datasource UID |

Twenty-three sections on InfluxDB and twenty-two on Prometheus — twenty-two
named rows plus the not-available row, except that Flash wear has no PromQL
and so ships no row there at all. (`sections.go` declares two more, Pressure
stall (PSI) and Block devices, which produce no row on the reference device
because its kernel and its idle nbd devices give them nothing to show.)
Ordered by how often they are opened: an Overview of thirteen panels, 31 grid
units tall, which does not fit a phone screen, then CPU, Memory and load,
Connections, Interface traffic, Detections and captures, and the families that
explain those when one looks wrong (the receive path, forwarding cost,
interrupts, temperature and clock, the kernel log), then the deliberate deep
tiers (busy runs, fragmentation, reclaim, PMU, flash wear, NAND health, the API
cross-checks, the observer and its sampler timing, and the device as the agent
established it). A panel whose measurement the store does not hold is routed
into a collapsed "Not available on this device" row with its query removed.
Every detection and trigger marker is also a dashboard annotation.

The alert rules are the panels' own fault counters and the collector's
detections, fifteen in all (`internal/dashboards/alerts.go`): agent silent,
kernel RX drops, OOM kills, any detection, a thermal zone within 15 % of its
own critical trip, the connection table above 80 % of `nf_conntrack_max`,
slipped ticks, the agent's own OOM, a layer-2 loop signature, a port's link
going down, typed MAC errors on a port, a bridge port the bridge has stopped
delivering to, a wake-up storm, egress-queue drops every minute for ten
minutes, and an uncorrectable ECC failure. Prometheus carries all fifteen;
InfluxDB has no slipped-ticks rule, and PostgreSQL has neither that nor the
layer-2 loop, link-down and port-error rules. No threshold is a compiled
number about the device: each is zero, fewer than one sample in two minutes
(agent silent), a share of a ceiling the device declares (80 % of the connection
table, 85 % of a zone's critical trip), or, for the wake-up storm, four times
the device's own rate over its previous day. [Alert rules](https://jmrp.io/docs/mikroscope/dashboards/alerts/)
gives each rule, what it fires on, and the backtests behind the newer ones.

## Importing

Grafana → Dashboards → New → Import → upload the file; Grafana asks which
datasource to bind. Or from the CLI, which also **checks** every panel on the
real Grafana the way ghchronicle does:

```sh
export GRAFANA_URL=http://grafana:3000 GRAFANA_TOKEN=…
mikroscope dashboards import --store influxdb --datasource-uid <uid>
mikroscope dashboards check  --store influxdb --datasource-uid <uid> --window 15m
```

`check` runs each panel's queries through `/api/ds/query` and fails on a panel
that returns no rows, or whose queries report an error — a dashboard is not
done until every panel returns data. The one exemption is a panel already
routed to the "Not available on this device" row: that one is tolerated either
way and counted separately in the summary line, because its measurement is
known to be absent from this store.

## InfluxDB 3 datasource

Type `influxdb`, `version: SQL`, `dbName: mikroscope`, and **both** secure
fields: `httpHeaderValue1 = "Bearer <token>"` (HTTP) and `token = <token>`
(FlightSQL). Without the second, panels fail with `flightsql: Unauthenticated`
(Grafana 12.3.2, 2026-09-12).

## What the queries accommodate

The reference RB5009's background squeeze rate makes "any squeeze" its norm — a
rule written that way fired 92 times in twenty minutes on it (RouterOS 7.24.2,
2026-09-15) — so the microburst rule takes an episode of three deviations
instead. `cluster` is reserved in DataFusion, and Prometheus 3 writes
`le="0.0"`, so the queries avoid the one and match the other. The per-poll
fast-path share is bytes-weighted per bin, because unweighted it swings 0-100 %
on interfaces moving a few packets. Grafana's Prometheus tables carry
`Time`/`__name__`/`instance`/`job` columns, which the table panels drop, and the
families that only appear after their first event are rendered at 0 from the
start, so a healthy router's panels stay out of the not-available row.

## Verified

2026-09-16, on the same Grafana and stores, with the collector restarted on
the build that adds the interface inventory and the kernel-log port events:
`dashboards check` over a 30-minute window: InfluxDB 171 panels, 0 failing, 10
known-empty tolerated (the two port-event panels, the opt-in conntrack poll,
the two trigger panels, PSI, the four idle block devices); Prometheus 133
panels, 0 failing, 9 known-empty tolerated. The two port-event SQL queries were
run against a synthetic table in the same InfluxDB 3, because the live store
had held no port record with a kind yet. The render walk below covers the
168/130-panel version and has not been repeated for the three new panels.

2026-09-15, on the owner's Grafana 13.2.1: a fresh `install` of the agent on
the reference RB5009 (RouterOS 7.24.2, privileged, the default triggers),
`forward --prom :9124 --influx … --interfaces bridge,ether1,PPPoE_DIGI
--counters-every 10s` for 30 minutes into the isolated InfluxDB 3 Core
(`InfluxDB_Mikroscope`), and a Prometheus 3.14 scraping the collector every 5 s
plus the agent directly for the families the collector cannot recompute.
`dashboards check` on both stores over a 30-minute window: InfluxDB 168 panels,
0 failing, 6 known-empty tolerated (the opt-in conntrack poll, PSI, the four
idle block devices); Prometheus 130 panels, 0 failing, 11 known-empty tolerated.
A headless row-by-row walk of both dashboards (Chromium, 1600x1000): 168 and 130
panels rendered, 0 error badges, 0 "No data".

2026-09-12, on the owner's Grafana 12.3.2: the InfluxDB dashboard against an
isolated InfluxDB 3 Core instance fed by `mikroscope forward` from an RB5009
— every panel returned rows (158–316 per panel over 10 min); the Prometheus
dashboard against a Prometheus 3.14 scraping the collector every 5 s —
every panel returned rows (228–2 052 over 5 min).
