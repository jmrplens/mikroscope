## Short answers

Ten questions about mikroscope on MikroTik RouterOS, from MIPS and 7.24 to cost, safety and cpu-load, each answered from the page that has the measurement.

Source: <https://jmrp.io/docs/mikroscope/start/questions/>

Each answer below is the short form of a page that has the evidence, and links to it. A figure
here is the one that page gives, with the device, the RouterOS version and the date beside it.

### Does mikroscope run on MIPS or TILE routers?

No. The agent runs in a RouterOS container, and MikroTik ships the `container` package for arm,
arm64, x86 and CHR only ([MikroTik's package
list](https://help.mikrotik.com/docs/spaces/ROS/pages/40992872/Packages)). mikroscope builds its
agent for arm64, arm and x86_64. On a MIPS or TILE board, SNMP or an API exporter is the tool:
[when not to use mikroscope](https://jmrp.io/docs/mikroscope/start/compared/#when-not-to-use-mikroscope).

### Which routers has it actually run on?

One: an arm64 RB5009UG+S+, on RouterOS 7.24.2 and later 7.24.4. The arm and x86_64 builds are
cross-built and checked in CI and have never run on hardware, and the hEX S that will test 32-bit
RouterOS has not arrived. Every figure on this site comes from that one router: [what it
is](https://jmrp.io/docs/mikroscope/start/).

### Why does it need RouterOS 7.24 or later?

The container step writes `privileged=`, an attribute RouterOS added in 7.24, whatever
`--privileged` says, so on an earlier 7.x that step is expected to fail, and the install removes the
tar it uploaded when that step fails. That is read from the code: no install has been tried on a RouterOS
before 7.24. Installs have run on 7.24.2 and 7.24.4 and nothing else: [a container-capable
device](https://jmrp.io/docs/mikroscope/install/prerequisites/#a-container-capable-device).

### Why does device-mode need a button press?

MikroTik built it that way. Device-mode limits what a router allows, to protect it from an
attacker who gained access, so changing it takes physical access: after `/system/device-mode/update
container=yes`, someone presses the reset or mode button, or power-cycles the router, within five
minutes ([MikroTik's device-mode
page](https://help.mikrotik.com/docs/spaces/ROS/pages/93749258/Device-mode)). No tool can do it
remotely: [device-mode container=yes](https://jmrp.io/docs/mikroscope/install/prerequisites/#device-mode-containeryes).

### What does it cost the router?

At the install default of 10 Hz the agent costs 2.69 % of one core
and 13.2 MiB of memory, read from its own cgroup, and 16.83 %
at 100 Hz. That is over the project's own CPU budget of 2 % and inside its
memory budget of 16 MiB: [the cost of the observer](https://jmrp.io/docs/mikroscope/cost/).

Measured on RB5009UG+S+ · 4 × 1.4 GHz Cortex-A72 · RouterOS 7.24.2 · 2026-09-18 · 300 s windows at steady state (ring full), full source set, the shipped configuration — a 60 s ring, the memory limit derived from it and the default 64M container cap — with the collector forwarding to InfluxDB 3

### Is it safe to run on a production router?

It was built on one: the reference RB5009 is the owner's production router. The agent never
connects out and presents no credential. Every write is listed before it is made, and tagged, and a
scripted round trip left the router's `/export` byte-identical (RB5009UG+S+, RouterOS 7.24.2, 2026-09-12).
It runs `privileged=yes`, a real grant: [what runs where](https://jmrp.io/docs/mikroscope/security/).

### Does it see interface traffic?

Not from inside the container. `/proc/net/dev` and the other network files are per network
namespace, so there they count the container's own veth, and `privileged=yes` does not change
that. Per-interface bytes and packets come from the RouterOS API, which the collector merges on the
agent's clock: [the container's network](https://jmrp.io/docs/mikroscope/limits/namespaces/#the-network-is-the-containers-own).

Measured on RB5009UG+S+ · 4 × 1.4 GHz Cortex-A72 · RouterOS 7.24.2 · 2026-09-12 · `privileged=yes` does not change the network namespace

### How many seconds does RouterOS `cpu-load` average over?

About one. Fitted against the kernel's own `/proc/stat` busy ratio read at 10 Hz on an RB5009,
`cpu-load` tracked a trailing mean of about a second that reached the API a fraction of a second
late, in each of two separate hours, and a sixty-second average is ruled out. The fits are on [the
RouterOS API tier](https://jmrp.io/docs/mikroscope/sinks/api-tier/#how-many-seconds-does-routeros-cpu-load-average-over).

Measured on RB5009UG+S+ · 4 × 1.4 GHz Cortex-A72 · RouterOS 7.24.2 · Linux 5.6.3 · 2026-09-15 · `/system/resource` polled at 1 Hz against the agent's per-core busy ratio at 10 Hz, two separate hours

### Does it replace SNMP or mktxp?

No. It does not replace the RouterOS API either, and takes per-interface traffic from it. What it
adds is the kernel's own view, which none of the others is documented to read: per-core ticks at
up to 100 Hz, softirqs, softnet drops and squeezes, and the kernel log. Where no container runs,
SNMP or mktxp is the tool: [the comparison](https://jmrp.io/docs/mikroscope/start/compared/).

### Does the agent send anything off the router?

No. It serves HTTP on its veth address and makes no outbound connection, and there is no update
check. Your collector pulls from it, and every sink token and API credential stays on your host,
because whatever sits in the container's envlist is treated as readable by every RouterOS user with
`read`: [what runs where](https://jmrp.io/docs/mikroscope/security/).

## Compared with the alternatives

What SNMP, The Dude, Graphing, the Profiler, mktxp and mikrotik-exporter read on a MikroTik router, beside mikroscope, and when to use them instead.

Source: <https://jmrp.io/docs/mikroscope/start/compared/>

mikroscope reads a MikroTik router's Linux kernel from inside a RouterOS container, at 1 to
100 Hz. SNMP, The Dude, RouterOS's own Graphing and Profiler, mktxp and mikrotik-exporter read
what RouterOS itself reports. This page sets the seven side by side, says where each cell comes
from, and says when one of the other six is the better choice.

### What `cpu-load` is, for the two exporters

mktxp and mikrotik-exporter both read `cpu-load`, which MikroTik defines as the percentage of used
CPU resources with all CPUs combined. On an RB5009 this project measured it as [a trailing mean of
about one second](https://jmrp.io/docs/mikroscope/sinks/api-tier/#how-many-seconds-does-routeros-cpu-load-average-over),
so a burst shorter than that second is averaged into it. Per-core figures exist in RouterOS's
`/system/resource/cpu`, which mikroscope's API tier reads and neither exporter's source asks for.

### What only the kernel showed

On 2026-09-12 a layer-2 loop on the reference router's production network left RouterOS's log and
port monitor reporting a healthy device, while the kernel log carried the router's own address
coming back into the bridge every STP hello. mikroscope found it through `/dev/kmsg`, and none of
the other six is documented as reading that log. [A loop only the kernel could
see](https://jmrp.io/docs/mikroscope/playbooks/loop/) has the diagnosis.

It does not replace the RouterOS API either: per-interface bytes and packets come from that API,
and the collector merges them with the kernel's samples on the agent's clock.

### When not to use mikroscope

- **A MIPS, TILE or PPC router.** The agent is nothing without a container, and MikroTik ships the
  `container` package for arm, arm64, x86 and CHR only. `/system/resource/print` names your
  router's `architecture-name`. SNMP, or an API exporter such as mktxp, reads what RouterOS reports
  on any of them.
- **RouterOS older than 7.24.** The container step writes `privileged=`, an attribute RouterOS added
  in 7.24, so on an earlier 7.x that step is expected to fail. That is read from the code: no install
  has been tried there. Upgrade RouterOS, or use SNMP or mktxp, neither of which needs a container.
- **No `container` package, or nobody to press the button.** `device-mode container=yes` takes a
  press of the reset or mode button, or a cold reboot, within five minutes of the command.
  [MikroTik's device-mode page](https://help.mikrotik.com/docs/spaces/ROS/pages/93749258/Device-mode)
  requires physical access on purpose, so no remote session can grant it. SNMP needs a service
  turned on, and an exporter an API user.
- **Interface traffic at a scrape interval is all you want.** mikroscope takes per-interface bytes
  and packets from the same RouterOS API an exporter reads, because the container cannot see them.
  An exporter gets them without putting anything on the router.
- **You need it proven on your board first.** Every run so far was on one arm64 RB5009; the arm and
  x86_64 builds are cross-built and checked in CI and have never run on hardware.
  [Where the project stands](https://jmrp.io/docs/mikroscope/about/status/) keeps that list.
